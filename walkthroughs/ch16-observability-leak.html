⚠ Predicted failure

  • Pitfall: Relying only on logs for latency problems.
  • Pitfall: Restarting on a schedule and calling the leak solved.

✓ Best troubleshooting path

  • Reproduce with the diagnostic command (step 1-2).
  • Think of a car diagnostic: the dashboard lights (metrics), the error log (logs), the route map with timings (traces), and finally putting the engine on a test bench (profiler).
  • Prometheus with Grafana covers metrics and lets you line up a latency spike against CPU throttling. Loki or an EFK stack centralises logs. OpenTelemetry instruments code to emit traces that Jaeger or Zipkin display as a waterfall, so a slow call across five services is obvious. Profilers such as pprof or JVM tools find the function responsible. VPA can suggest right-sized requests, and KEDA scales on event sources like queue depth.
  • Case: a service slowed and restarted every few days. Grafana showed memory rising for 48 hours then dropping to zero at an OOM restart. A heap dump during high usage revealed a cache that grew without bound. They fixed the eviction logic and added an alert on abnormal memory growth.
  • Apply the fix command (step 3), then verify (step 4).
  • Confirm status becomes Running.

Key points

  • Metrics, logs and traces each answer a different question.
  • Tracing is the right tool for latency across many services.
  • Sawtooth memory with restarts suggests a leak.
  • Alert on trends, not just thresholds.
  • Profile before scaling; scaling a leak only delays it.
