Chapter 16 · Real-World Troubleshooting Scenarios · SENIOR

An API becomes very slow under load but never crashes and CPU looks flat. What could it be?

Chapter 16 senior walkthrough · 4 steps
Say first

CPU throttling: a container at its CPU limit is paused by the kernel scheduler for the rest of each period, so latency rises without any restart or event. The proof is in throttling metrics, not in kubectl events.

⚠ Predicted failure

  • Pitfall: Reading flat CPU usage as 'the app is idle'.
  • Pitfall: Setting tiny CPU limits on latency-sensitive services.
  • If ignored, this surfaces as: CrashLoopBackOff.

✓ Best troubleshooting path

  • Reproduce with the diagnostic command (step 1-2).
  • CPU is a tap with a flow restrictor, memory is a tank with a hard lid. Exceed the CPU limit and the tap just slows; exceed the memory limit and the container is removed.
  • The trap: kubectl top shows CPU pinned at exactly the limit, which does not look like an error. Prove it with Prometheus: a rising container_cpu_cfs_throttled_periods_total, or the ratio of throttled to total periods. Compare the limit in describe with usage, and check whether the whole node is out of CPU (kubectl top node), which would need more capacity, not a different limit.
  • Case: an API with a 500m limit went from 50 ms to over 2000 ms under load; usage sat flat at 500m with throttling climbing. Removing the CPU limit but keeping the 500m request let it burst to about 1.5 cores and latency stayed low while they optimised a hot function.
  • Apply the fix command (step 3), then verify (step 4).
  • Confirm status becomes Running.

Explain

  • CPU is a tap with a flow restrictor, memory is a tank with a hard lid. Exceed the CPU limit and the tap just slows; exceed the memory limit and the container is removed.
  • The trap: kubectl top shows CPU pinned at exactly the limit, which does not look like an error. Prove it with Prometheus: a rising container_cpu_cfs_throttled_periods_total, or the ratio of throttled to total periods. Compare the limit in describe with usage, and check whether the whole node is out of CPU (kubectl top node), which would need more capacity, not a different limit.
  • Case: an API with a 500m limit went from 50 ms to over 2000 ms under load; usage sat flat at 500m with throttling climbing. Removing the CPU limit but keeping the 500m request let it burst to about 1.5 cores and latency stayed low while they optimised a hot function.
  • Rule of thumb: always set a CPU request; set a CPU limit only when you need a hard cap or Guaranteed QoS for predictability, and watch throttling if you do.

Key points

  • CPU over limit means throttled; memory over limit means killed.
  • No event is raised for throttling; use metrics.
  • Usage flat against the limit plus high latency is the signature.
  • Requests govern scheduling and fair share; limits cap bursts.
  • Profile the code before buying more CPU.
