How does service discovery work with cluster DNS?

Chapter 2 mid walkthrough · 4 steps
Say first

CoreDNS runs as Pods behind a cluster service; every Pod is configured to send DNS queries to it, so a Service name resolves to its stable ClusterIP regardless of Pod churn.

⚠ Predicted failure

  • Pitfall: Saying DNS load balances across Pods; it returns the Service IP and the data path spreads traffic.
  • If ignored, this surfaces as: NotReady.

✓ Best troubleshooting path

  • Reproduce with the diagnostic command (step 1-2).
  • Pod IPs change constantly, so applications use names. Think of a phone book that updates itself whenever someone moves.
  • A Service named db in namespace shop becomes db.shop.svc.cluster.local. From the same namespace the short name db also works because of the search domains in the Pod's resolv.conf.
  • Names outside the cluster domain are forwarded to upstream resolvers. CoreDNS is the default; the older kube-dns is superseded because CoreDNS is more extensible through plugins. Load spreading happens at the Service layer, not in DNS.
  • Apply the fix command (step 3), then verify (step 4).
  • Confirm status becomes Ready.

Explain

  • Pod IPs change constantly, so applications use names. Think of a phone book that updates itself whenever someone moves.
  • A Service named db in namespace shop becomes db.shop.svc.cluster.local. From the same namespace the short name db also works because of the search domains in the Pod's resolv.conf.
  • Names outside the cluster domain are forwarded to upstream resolvers. CoreDNS is the default; the older kube-dns is superseded because CoreDNS is more extensible through plugins. Load spreading happens at the Service layer, not in DNS.

Key points

  • Stable name, changing IPs behind it.
  • CoreDNS is the default cluster DNS.
  • The cluster DNS Service keeps the same IP for all Pods.
  • Corefile ConfigMap customises behaviour.
