What is a container, and what problem does it solve?

Chapter 1 junior walkthrough · 4 steps
Say first

A container is a packaged, isolated process that carries its code, runtime and libraries with it, so it behaves the same on a laptop, in test and in production.

⚠ Predicted failure

  • Pitfall: Calling a container 'a small VM'. It shares the host kernel and is just an isolated process.
  • Pitfall: Saying the image is the running thing. The image is read-only; the container is the running instance.
  • If ignored, this surfaces as: CrashLoopBackOff.

✓ Best troubleshooting path

  • Reproduce with the diagnostic command (step 1-2).
  • Think of a shipping container. The crane does not care whether it holds shoes or engines, because the box is a standard size and sealed. A software container does the same for an application: whatever is inside, every machine knows how to run the box.
  • The classic pain is 'it works on my machine'. The app depended on a library version or setting that only existed on the developer's laptop. Packing the app together with those dependencies removes the difference between environments.
  • The packaged form is called an image. A container is a running instance of that image, and it normally runs one main process (the entrypoint) isolated from the host and from other containers.
  • Apply the fix command (step 3), then verify (step 4).
  • Confirm status becomes Running.

Explain

  • Think of a shipping container. The crane does not care whether it holds shoes or engines, because the box is a standard size and sealed. A software container does the same for an application: whatever is inside, every machine knows how to run the box.
  • The classic pain is 'it works on my machine'. The app depended on a library version or setting that only existed on the developer's laptop. Packing the app together with those dependencies removes the difference between environments.
  • The packaged form is called an image. A container is a running instance of that image, and it normally runs one main process (the entrypoint) isolated from the host and from other containers.

Key points

  • Image = the package; container = a running copy of it.
  • Contains code, runtime, system libraries and settings, not a whole operating system.
  • Same image runs identically from development to production.
  • Usually one main process per container.
  • Isolation keeps one container from interfering with its neighbours.
