You applied an egress policy allowing only GitHub on port 443, and the Pod now fails with a DNS timeout. Why, and how do you fix it?

Chapter 9 senior walkthrough · 4 steps
Say first

Egress is now deny-by-default, so the DNS lookup to kube-dns is blocked too. I add an egress rule that allows UDP 53 to the kube-dns Pods in kube-system.

⚠ Predicted failure

  • Pitfall: Hard-coding an IP that later changes
  • Pitfall: Forgetting DNS when writing deny-by-default
  • If ignored, this surfaces as: Forbidden.

✓ Best troubleshooting path

  • Reproduce with the diagnostic command (step 1-2).
  • The Pod needs two things to reach github.com: a name lookup and then a connection. The policy allowed only the connection to the IP, so the lookup died, giving a resolving timeout.
  • The fix is a second egress block selecting kube-system by its automatic namespace label and the k8s-app: kube-dns Pods, on UDP 53. Many clusters also need TCP 53 for large responses.
  • Pinning an IP is fragile because GitHub's addresses change. Plain NetworkPolicy cannot match domain names, which leads to CNI-specific policies.
  • Apply the fix command (step 3), then verify (step 4).
  • Confirm status becomes Allowed.

Explain

  • The Pod needs two things to reach github.com: a name lookup and then a connection. The policy allowed only the connection to the IP, so the lookup died, giving a resolving timeout.
  • The fix is a second egress block selecting kube-system by its automatic namespace label and the k8s-app: kube-dns Pods, on UDP 53. Many clusters also need TCP 53 for large responses.
  • Pinning an IP is fragile because GitHub's addresses change. Plain NetworkPolicy cannot match domain names, which leads to CNI-specific policies.

Key points

  • Selecting a Pod for egress flips it to deny-by-default for outgoing traffic
  • Always allow DNS when restricting egress
  • Use kubernetes.io/metadata.name to select a namespace
  • Test by reading the Pod logs
