What is the difference between a Deployment and a ReplicaSet?

Chapter 3 mid walkthrough · 4 steps
Say first

A ReplicaSet only maintains a count of identical Pods; a Deployment sits above it and manages ReplicaSets to give you rolling updates, rollbacks and history.

⚠ Predicted failure

  • Pitfall: Editing the generated ReplicaSet by hand; the Deployment will overwrite it.
  • If ignored, this surfaces as: Progressing.

✓ Best troubleshooting path

  • Reproduce with the diagnostic command (step 1-2).
  • Think of the ReplicaSet as the staff roster for one version of the app, and the Deployment as the manager who swaps rosters when a new version ships.
  • Each change to the Pod template creates a new ReplicaSet. The Deployment scales it up while scaling the old one down, and keeps old ReplicaSets (at zero replicas) so a rollback is just scaling the old one back up.
  • In practice you almost never create ReplicaSets directly; you declare the desired state in a Deployment and let it do the work.
  • Apply the fix command (step 3), then verify (step 4).
  • Confirm status becomes Available.

  • In practice you almost never create ReplicaSets directly; you declare the desired state in a Deployment and let it do the work.

Key points

  • Deployment manages ReplicaSets, which manage Pods.
  • One ReplicaSet per revision of the Pod template.
  • Gives declarative updates, rollbacks and revision history.
  • Best fit for stateless apps where any Pod is interchangeable.
