How would you set up a GitOps workflow with Kubernetes from scratch?

Chapter 11 mid walkthrough · 4 steps
Say first

Create a Git repo for manifests, wire CI to validate changes, install a GitOps operator such as Argo CD or Flux in the cluster, point it at the repo, and add monitoring and alerts.

⚠ Predicted failure

  • Pitfall: Giving the CI system cluster-admin credentials, which defeats the security benefit of pull.
  • If ignored, this surfaces as: OutOfSync.

✓ Best troubleshooting path

  • Reproduce with the diagnostic command (step 1-2).
  • Step one is the repo: it becomes the single source of truth for manifests. Step two is CI, using Jenkins, GitLab CI or GitHub Actions to lint and validate changes and to build images, but not to deploy into the cluster directly.
  • Step three is installing the operator in the cluster and giving it a source (the repo, a path and a revision) plus a destination (cluster and namespace). Optionally add a Git webhook so changes are noticed in seconds rather than at the next poll.
  • Finally, watch the system itself. Prometheus and Grafana can show sync status, failures and reconcile duration, and alerts should fire when an app stays OutOfSync or Degraded.
  • Apply the fix command (step 3), then verify (step 4).
  • Confirm status becomes Synced.

  • Step three is installing the operator in the cluster and giving it a source (the repo, a path and a revision) plus a destination (cluster and namespace). Optionally add a Git webhook so changes are noticed in seconds rather than at the next poll.

Key points

  • Repo as the source of truth
  • CI validates and builds; the operator deploys
  • Operator needs source repo and destination cluster/namespace
  • Webhooks speed detection but reconciliation stays pull-based
  • Monitor the GitOps tooling, not just the apps
